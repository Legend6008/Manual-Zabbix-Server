    Solución de errores SSH mediante comandos¶

    1. Error: Permission denied (publickey)¶

    Causa: el servidor no reconoce la clave pública del cliente.

    En Windows 11 (PowerShell):

    Verificar que existan las claves SSH:

    Get-ChildItem "$env:USERPROFILE\.ssh"

    Conectarse indicando la clave privada:

    ssh -i "$env:USERPROFILE\.ssh\id_ed25519" ubuntu@100.84.117.85

    Mostrar la clave pública para copiarla:

    Get-Content "$env:USERPROFILE\.ssh\id_ed25519.pub"

    En Ubuntu Server:

    Crear el directorio y el archivo para autorizar la clave pública, si no existen:

    mkdir -p ~/.ssh
nano ~/.ssh/authorized_keys

    Pegar la clave pública completa en una línea y guardar. Después, establecer los permisos:

    chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys

    2. Error: Connection timed out¶

    Causa: el cliente no logra alcanzar el servidor por la red o el puerto SSH está bloqueado.

    En Windows 11 (PowerShell):

    Verificar la conexión con Tailscale:

    tailscale status
tailscale ping 100.84.117.85

    Comprobar si el puerto SSH está accesible:

    Test-NetConnection 100.84.117.85 -Port 22

    En Ubuntu Server:

    Comprobar el estado del servicio SSH:

    sudo systemctl status ssh

    Revisar las reglas del firewall:

    sudo ufw status verbose

    Si el firewall bloquea el acceso, permitir SSH por la interfaz de red correspondiente:

    sudo ufw allow 22/tcp

    Seguridad: si solo necesitás administrar el servidor mediante Tailscale, es preferible limitar SSH a esa red en lugar de abrir el puerto indiscriminadamente en todas las interfaces. Verificá las reglas antes de modificarlas para no perder el acceso remoto.

    3. Error: Connection refused¶

    Causa: el servidor responde, pero no acepta conexiones en el puerto solicitado; por ejemplo, porque SSH está detenido.

    En Ubuntu Server:

    sudo systemctl status ssh
sudo systemctl start ssh
sudo systemctl enable ssh

    Si el servicio no está instalado:

    sudo apt update
sudo apt install openssh-server -y
sudo systemctl enable --now ssh

    Verificar que esté escuchando en el puerto 22:

    sudo ss -tlnp | grep ':22'

    4. Error: ssh-copy-id no se reconoce en Windows¶

    Causa: Windows normalmente no incluye ssh-copy-id de forma predeterminada.

    Solución: mostrar la clave pública en PowerShell:

    Get-Content "$env:USERPROFILE\.ssh\id_ed25519.pub"

    Copiarla y agregarla manualmente en Ubuntu, dentro de:

    nano ~/.ssh/authorized_keys

    Luego, aplicar los permisos correspondientes:

    chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys

    5. Error: Could not resolve hostname¶

    Causa: el nombre del servidor está mal escrito o no puede resolverse mediante DNS.

    En Windows 11 (PowerShell):

    Comprobar que Tailscale esté conectado:

    tailscale status

    Probar la conexión utilizando la IP de Tailscale del servidor:

    ssh ubuntu@100.84.117.85

    6. Error: Host key verification failed¶

    Causa: la clave de identificación del servidor cambió o no coincide con la guardada en el cliente.

    En Windows 11 (PowerShell):

    Primero, verificar por un medio confiable que la clave del servidor haya cambiado legítimamente. Si se confirma, eliminar la entrada antigua:

    ssh-keygen -R 100.84.117.85

    Después, volver a conectar:

    ssh ubuntu@100.84.117.85

    Aceptar la nueva clave únicamente después de verificar su autenticidad.

    7. Comandos de diagnóstico rápido¶

    En Windows 11 (PowerShell):

    tailscale status
tailscale ping 100.84.117.85
Test-NetConnection 100.84.117.85 -Port 22
ssh -v ubuntu@100.84.117.85

    El parámetro -v muestra información de diagnóstico durante el intento de conexión.

    En Ubuntu Server:

    sudo systemctl status ssh
sudo ss -tlnp | grep ':22'
sudo ufw status verbose
sudo journalctl -u ssh -n 50 --no-pager

    Estos comandos permiten revisar el servicio, el puerto, el firewall y los últimos mensajes del servicio SSH.

    Recomendación final¶

    Antes de modificar la configuración, identificá el mensaje exacto del error y ejecutá primero los comandos de diagnóstico. Evitá desactivar el firewall o habilitar el acceso SSH de root como solución general.

    Buenas prácticas de seguridad¶

    Utilizar claves SSH en lugar de depender exclusivamente de contraseñas cuando la configuración lo permita.

    Proteger la clave privada y evitar compartirla o enviarla a otras personas.

    Utilizar una contraseña para proteger la clave privada.

    Mantener actualizado el servicio OpenSSH.

    Limitar el acceso SSH a usuarios autorizados.

    Evitar exponer el puerto 22 directamente a Internet cuando sea posible utilizar una VPN.

    Verificar la identidad del servidor antes de aceptar una nueva clave de host.

    Mantener las reglas del firewall restringidas a las conexiones necesarias.
