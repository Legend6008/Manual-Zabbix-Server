    Creacion y Configuración de alertas¶

    A tener en cuenta: los hostnames, se deben remplazar por los nombres reales registrados en zabbix.

    1. Espacio libre en disco¶

    Equipo: NOTEBOOK UBUNTU
    Objetivo: detectar cuándo el espacio libre de la partición raíz es insuficiente.

    1.1. Crear el item¶

    1. Ingresar a la interfaz web de Zabbix.
    2. Ir a Data collection → Hosts.
    3. Seleccionar el host correspondiente a NOTEBOOK UBUNTU.
    4. Abrir la pestaña Items y presionar Create item.
    5. Completar los siguientes campos:
    Campo Valor
    Name Espacio libre en la particion raíz
    Type Zabbix agent
    Key vfs.fs.size[/,pfree]
    Type of information Numeric (float)
    Host Interface 127.0.0.1:10050
    Units %
    Update interval 1s
    Enabled Sí

    1. Guardar el item con Add.

    Este item mide el porcentaje de espacio libre de la partición raíz /.

    1.2. Crear el trigger¶

    1. Ingresar al host y abrir la pestaña Triggers.
    2. Presionar Create trigger.
    3. Completar los campos:
    Campo Valor
    Name Poco espacio libre en disco raiz (<10%)
    Severity High
    Expression last(/NOTEBOOK_UBUNTU/vfs.fs.size[/,pfree])<10

    1. Guardar el trigger.

    Funcionamiento: se genera una alerta cuando queda menos del 10 % de espacio libre.

    Forzarmor alerta espacio libre en disco:¶

    Para forzar la alerta de poco espacio en disco en tu Ubuntu, puedes llenar temporalmente espacio en la partición raíz con fallocate. Opción recomendada Primero verifica el espacio disponible: 

    df -h /

    Luego crea un archivo grande:

    sudo fallocate -l 10G /tmp/zabbix-test.img

    Verifica nuevamente:

    df -h /

    Si tu trigger se activa cuando el espacio libre baja, aumenta el tamaño según sea necesario:

    sudo fallocate -l 20G /tmp/zabbix-test.img

    Para eliminar el archivo y recuperar el espacio

    sudo rm /tmp/zabbix-test.img

    Y verifica:

    df -h /

    Importante: no debemos llenar el disco completamente. Deja siempre algo de espacio libre para evitar problemas en Ubuntu.

    2. Uso de CPU¶

    Equipo: Notebook Ubuntu

    Objetivo: detectar un uso excesivo del procesador durante varios minutos.

    2.1. Crear el item¶

    1. Ingresar a Data collection → Hosts.
    2. Seleccionar Notebook Ubuntu.
    3. Abrir Items → Create item.
    4. Configurar:
    Campo Valor
    Name Linux: CPU idle time
    Type Zabbix agent
    Key system.cpu.util[,idle]
    Type of information Numeric (float)
    Units %
    Update interval 10s
    Enabled Sí

    1. Presionar Add.

    El item mide el porcentaje de tiempo de CPU utilizado en modo sistema.

    2.2. Crear el trigger¶

    1. Abrir Triggers → Create trigger.
    2. Completar:
    Campo Valor
    Name Alerta por uso elevado de CPU
    Severity High
    Expression avg(/adrian/system.cpu.util[,idle],5m)<60

    Forzar alerta por alto uso de CPU¶

    Para comprobar el funcionamiento de una alerta de alto uso de CPU en Zabbix, podemos generar una carga temporal en el equipo Ubuntu.

    Instalar stress-ng¶

    Primero, actualizamos los repositorios e instalamos la herramienta:

    sudo apt update
sudo apt install stress-ng -y

    stress-ng permite generar carga controlada sobre diferentes recursos del sistema, como CPU, memoria y disco.

    Forzar el uso de CPU¶

    Para utilizar todos los núcleos disponibles durante 5 minutos, ejecutamos:

    stress-ng --cpu 0 --timeout 5m

    Explicación de los parámetros¶

    • --cpu 0: utiliza todos los núcleos disponibles del procesador.
    • --timeout 5m: mantiene la carga durante 5 minutos.

    Durante este período, Zabbix debería detectar el aumento en la utilización del procesador. Si el valor supera el umbral configurado en el trigger, se generará una alerta.

    Detener la prueba antes de tiempo¶

    Si necesitamos finalizar la prueba antes de que termine el tiempo configurado:

    pkill stress-ng

    Este comando finaliza los procesos de stress-ng que se encuentren ejecutándose.

    Importante: una vez finalizada la carga, el uso de CPU debería volver a valores normales y la alerta de Zabbix debería resolverse automáticamente, dependiendo de la configuración del trigger.

    1. Guardar el trigger.

    Funcionamiento: la alerta se activa cuando el uso de CPU en modo sistema supera el 85 % de promedio durante cinco minutos.

    Esta métrica mide específicamente el tiempo de CPU en modo sistema, no todo el uso del procesador. Para una alerta de uso total, conviene utilizar una métrica de utilización global de CPU.

    3. Memoria RAM disponible¶

    Equipo: WINDOWS 11 LTSC
    Objetivo: detectar una cantidad crítica de memoria RAM disponible.

    3.1. Crear el item¶

    1. Ir a Data collection → Hosts.
    2. Seleccionar el host de Windows 11 LTSC.
    3. Abrir Items → Create item.
    4. Configurar:
    Campo Valor
    Name Memoria RAM disponible
    Type Zabbix agent
    Key vm.memory.size[available]
    Type of information Numeric (float)
    Units %
    Update interval 1m
    Enabled Sí

    1. Presionar Add.

    El item registra el porcentaje de memoria disponible.

    3.2. Crear el trigger¶

    1. Ingresar a Triggers → Create trigger.
    2. Completar:
    Campo Valor
    Name Poca memoria RAM disponible
    Severity High
    Expression last(/agentwin11/vm.memory.size[available]<9663676416

    1. Guardar el trigger.

    3.3 Configurar la expresión de recuperación de memoria RAM en Windows 11¶

    Para que la alerta de memoria RAM se resuelva automáticamente cuando el equipo recupere suficiente memoria disponible, debemos configurar una Expresión de recuperación (Recovery expression) en el trigger de Zabbix.

    3.4 Expresión de problema¶

    Mantené la expresión original para activar la alerta cuando la memoria disponible sea inferior a 9 GiB:

    last(/agentwin11/vm.memory.size[available],#1) < 9663676416

    3.5 Expresión de recuperación¶

    En la configuración del trigger, habilitá la opción Recovery expression y colocá:

    last(/agentwin11/vm.memory.size[available],#1) > 9663676416

    3.6 Comportamiento que se espera¶

    Memoria disponible Estado
    Más de 9 GiB OK
    Menos de 9 GiB PROBLEM
    Vuelve a superar 9 GiB RECUPERADO

    Resultado¶

    Con esta configuración, Zabbix activa la alerta cuando la memoria disponible cae por debajo de 9 GiB y la resuelve automáticamente cuando vuelve a superar ese valor, sin necesidad de intervención manual.

    Importante: no reemplaces la expresión de problema. Ambas expresiones deben permanecer configuradas por separado: una para detectar el problema y otra para determinar su recuperación.

    Funcionamiento: la alerta se activa cuando la memoria disponible permanece por debajo del 10 % durante el período evaluado.

    Reemplazar agentwin11 por el nombre técnico real del host. Verificar que el agente instalado admita la clave vm.memory.size[pavailable].

    Forzar alerta en Ubuntu¶

    Para comprobar el funcionamiento de una alerta de memoria RAM disponible baja en Zabbix, podemos utilizar stress-ng para generar un consumo controlado de memoria en Ubuntu.

    Instalar la herramienta¶

    Actualizamos los repositorios e instalamos stress-ng:

    sudo apt update
sudo apt install stress-ng -y

    Generar consumo de memoria¶

    Para consumir aproximadamente 2 GB de RAM durante 5 minutos, ejecutamos:

    stress-ng --vm 1 --vm-bytes 2G --vm-keep --timeout 5m

    Explicación de los parámetros¶

    • --vm 1: crea un proceso que genera consumo de memoria.
    • --vm-bytes 2G: solicita aproximadamente 2 GB de memoria.
    • --vm-keep: mantiene la memoria ocupada durante la prueba.
    • --timeout 5m: establece una duración de 5 minutos.

    Durante este período, Zabbix debería detectar la disminución de memoria disponible. Si el valor cae por debajo del umbral configurado en el trigger, se generará una alerta.

    Verificar la memoria RAM disponible¶

    En otra terminal, ejecutamos:

    free -h

    Este comando permite consultar la memoria total, utilizada, disponible y el uso de swap.

    También podemos observar los procesos que consumen más memoria:

    top

    Detener la prueba¶

    Para finalizar la prueba antes de que termine el tiempo configurado:

    pkill stress-ng

    Una vez detenida la carga, la memoria utilizada debería liberarse y la alerta de Zabbix debería resolverse automáticamente, dependiendo de la expresión del trigger.

    Precaución¶

    No se recomienda consumir toda la memoria RAM del equipo. Ajustar los 2 GB según la capacidad disponible para evitar bloqueos, uso excesivo de swap o finalización de procesos por falta de memoria.

    Realizar esta prueba preferentemente en un entorno de laboratorio y supervisar el consumo durante su ejecución.

    Forzar alerta en Windows 11 LTSC¶

    Para comprobar el funcionamiento de una alerta de memoria RAM disponible baja en Zabbix, podemos utilizar PowerShell para reservar memoria temporalmente.

    Abrir PowerShell como administrador¶

    Abrir PowerShell con permisos de administrador y ejecutar:

    $buffers = @()

    Esta variable permitirá almacenar los bloques de memoria reservados durante la prueba.

    Consumir memoria RAM¶

    Para reservar aproximadamente 2 GB de memoria:

    $buffers += New-Object byte[] (2GB)

    Si necesitamos consumir más memoria, podemos agregar otro bloque:

    $buffers += New-Object byte[] (1GB)

    Repetir el comando hasta alcanzar el umbral configurado en el trigger de Zabbix.

    Verificar la memoria disponible¶

    En otra ventana de PowerShell, ejecutar:

    Get-CimInstance Win32_OperatingSystem | Select-Object @{Name="RAM_Libre_MB";Expression={[math]::Round($_.FreePhysicalMemory/1024,2)}}

    Este comando permite consultar la cantidad de memoria física disponible, expresada en MB.

    Durante la prueba, Zabbix debería detectar la disminución de memoria disponible y generar una alerta cuando se alcance el umbral configurado.

    Liberar la memoria¶

    Una vez que Zabbix registre el evento, ejecutar:

    $buffers = $null
[GC]::Collect()

    Esto elimina las referencias a los bloques reservados y solicita al recolector de basura de .NET que libere la memoria.

    Precaución¶

    No consumir toda la RAM del equipo. Ajustar la cantidad de memoria reservada según la capacidad disponible para evitar bloqueos, lentitud excesiva o un uso intensivo del archivo de paginación.

    Realizar esta prueba preferentemente en un entorno de laboratorio y supervisar el consumo durante su ejecución.

    4. Estado del servicio web¶

    Equipo: NOTEBOOK UBUNTU
    Objetivo: comprobar si el servicio HTTP responde en el puerto 80.

    4.1. Crear el item¶

    1. Seleccionar NOTEBOOK UBUNTU en Data collection → Hosts.
    2. Abrir Items → Create item.
    3. Configurar:
    Campo Valor
    Name Estado del servicio web HTTP
    Type Zabbix agent
    Key net.tcp.service[http,,80]
    Type of information Numeric (int 64 bits)
    Host name 127.0.0.1:10050
    Units Sin unidades
    Update interval 1m
    Enabled Sí

    1. Presionar Add.

    El item devuelve 1 si el servicio HTTP responde y 0 si no responde.

    4.2. Crear el trigger¶

    1. Ingresar a Triggers → Create trigger.
    2. Completar:
    Campo Valor
    Name Servicio web caído o inaccesible
    Severity Critical
    Expression last(/NOTEBOOK_UBUNTU/net.tcp.service[http,,80])=0

    1. Guardar el trigger.

    Funcionamiento: la alerta se activa cuando la comprobación no logra establecer comunicación con el servicio HTTP.

    Esta prueba verifica el servicio HTTP en el puerto 80 desde el equipo donde se ejecuta el agente. Si el servidor web utiliza HTTPS en el puerto 443, configurar la clave correspondiente. Si el servicio está en otro equipo, se debe comprobar la dirección de destino adecuada.

    Forzar una alerta por caída del servicio HTTP en Ubuntu¶

    Para comprobar el funcionamiento del ítem que monitorea el servicio web, vamos a detener temporalmente el servicio que utiliza el puerto 80.

    Verificar qué servicio utiliza el puerto 80¶

    Ejecutar en Ubuntu:

    sudo ss -tlnp | grep ':80'

    Esto permite identificar qué proceso está escuchando en el puerto 80.

    Detener el servicio¶

    Si utilizás Apache:

    sudo systemctl stop apache2

    Si se utiliza Nginx:

    sudo systemctl stop nginx

    Alerta esperada¶

    Zabbix debería detectar que el puerto 80 dejó de responder y activar el trigger, mostrando el estado PROBLEM.

    Comprobar que el puerto está cerrado¶

    Ejecutar:

    curl -I --max-time 5 http://localhost

    Deberías obtener un error de conexión porque el servicio HTTP está detenido.

    Recuperar el servicio¶

    Para iniciar Apache:

    sudo systemctl start apache2

    Para iniciar Nginx:

    sudo systemctl start nginx

    Verificar nuevamente que el servicio responda:

    curl -I http://localhost

    Resultado esperado¶

    Cuando el servicio HTTP vuelva a responder, Zabbix debería detectar la recuperación y cambiar automáticamente el estado de PROBLEM a OK.

    5. Linux CPU Idle Time¶

    Equipo: NOTEBOOK UBUNTU
    Objetivo: detectar cuándo la CPU dispone de muy poco tiempo de inactividad.

    5.1. Crear el item¶

    1. Seleccionar NOTEBOOK UBUNTU.
    2. Abrir Items → Create item.
    3. Configurar:
    Campo Valor
    Name Linux CPU Idle Time
    Type Zabbix agent
    Key system.cpu.util[,idle]
    Type of information Numeric (float)
    Units %
    Update interval 1m
    Enabled Sí

    1. Presionar Add.

    El item mide el porcentaje de tiempo durante el cual la CPU permanece inactiva.

    5.2. Crear el trigger¶

    1. Abrir Triggers → Create trigger.
    2. Completar:
    Campo Valor
    Name Alerta por bajo tiempo de inactividad
    Severity Warning
    Expression avg(/Notebook Ubuntu/system.cpu.util[,idle],5m)<10

    1. Guardar el trigger.

    Funcionamiento: la alerta se activa cuando el tiempo de inactividad de la CPU es inferior al 10 % en promedio durante cinco minutos.

    Esto puede indicar una carga elevada de procesamiento. Como el valor está relacionado con la utilización de CPU, conviene analizarlo junto con el item de uso de CPU para evitar alertas redundantes.

    Forzar una alerta por bajo CPU Idle Time en Ubuntu¶

    Para comprobar el funcionamiento del trigger de CPU Idle Time en Zabbix, vamos a generar una carga elevada en el procesador utilizando la herramienta stress-ng.

    Instalar stress-ng¶

    Si todavía no está instalada, ejecutar:

    sudo apt install stress-ng -y

    Generar carga de CPU¶

    Ejecutar el siguiente comando:

    stress-ng --cpu 0 --cpu-method matrixprod --timeout 5m

    Descripción de los parámetros:

    • --cpu 0: utiliza todos los núcleos disponibles.
    • --cpu-method matrixprod: realiza operaciones matemáticas intensivas para generar carga.
    • --timeout 5m: mantiene la carga durante cinco minutos.

    Verificar el uso de CPU¶

    En otra terminal, ejecutar:

    top

    También se puede utilizar:

    mpstat 1

    Si el comando mpstat no está disponible, instalar el paquete correspondiente:

    sudo apt install sysstat -y

    Detener la prueba¶

    Para finalizar el proceso antes de que termine el tiempo establecido:

    pkill stress-ng

    Resultado esperado¶

    Durante la prueba, el porcentaje de CPU Idle Time debería disminuir considerablemente.

    Si el valor cae por debajo del umbral configurado en el trigger de Zabbix (por ejemplo, menos del 10 %), se debería generar una alerta con estado PROBLEM.

    Al detener la prueba y recuperar la disponibilidad del procesador, el valor de CPU Idle Time debería aumentar y permitir que la alerta se resuelva automáticamente, siempre que la expresión de recuperación esté configurada.

    Importante: si el trigger detecta un CPU Idle inferior al 10 %, esta prueba debería ser suficiente en condiciones normales. El resultado puede variar según la cantidad de núcleos y la carga del equipo.

    6. Uptime¶

    Equipo: mauro
    Objetivo: detectar un reinicio reciente del equipo mediante su tiempo de actividad.

    6.1. Crear el item¶

    1. Ir a Data collection → Hosts.
    2. Seleccionar el host mauro.
    3. Abrir Items → Create item.
    4. Configurar:
    Campo Valor
    Name Tiempo de actividad del sistema
    Type Zabbix agent
    Key system.uptime
    Type of information Numeric (unsigned)
    Host name 100.112.1.18:10050
    Units uptime
    Update interval 1m
    Enabled Sí

    1. Presionar Add.

    El item devuelve el tiempo transcurrido desde el último inicio del sistema, expresado en segundos.

    6.2. Crear el trigger¶

    1. Abrir Triggers → Create trigger.
    2. Completar:
    Campo Valor
    Name Host reiniciado recientemente
    Severity Warning
    Expression last(/mauro/system.uptime)<600

    1. Guardar el trigger.

    Funcionamiento: se activa cuando el tiempo de actividad registrado es inferior a 600 segundos, es decir, diez minutos.

    La alerta se recupera automáticamente cuando el uptime supera ese umbral.

    Este método detecta un uptime bajo, pero no demuestra por sí solo la causa del reinicio. Para investigar reinicios inesperados, complementar con registros del sistema y eventos de apagado o arranque.

    7. Logs fallidos de inicio de sesión¶

    Equipo: mauro
    Objetivo: detectar múltiples intentos fallidos de autenticación en Linux.

    7.1. Verificar el registro de autenticación¶

    Antes de crear el item, comprobar si existe el archivo de autenticación:

    sudo ls -l /var/log/auth.log
```,,-           

Buscar eventos de autenticación fallida:

```bash
sudo grep -i "Failed password" /var/log/auth.log | tail -n 10

    Si el archivo no existe o no contiene eventos, verificar la configuración de rsyslog y el registro de autenticación utilizado por la distribución.

    7.2. Crear el item¶

    1. Seleccionar el host mauro en Zabbix.
    2. Abrir Items → Create item.
    3. Configurar:
    Campo Valor
    Name Intentos de login fallidos
    Type Zabbix agent (active)
    Key log[/var/log/auth.log,"Failed password"]
    Type of information Log
    Update interval 1s
    Enabled Sí

    Para comprobar el funcionamiento del trigger de detección de intentos fallidos de autenticación SSH, vamos a generar seis intentos de conexión con un usuario inexistente.

    El objetivo es superar el umbral configurado en Zabbix: más de 5 fallos en un período de 5 minutos.

    7.3. Crear el trigger¶

    1. Abrir Triggers → Create trigger.
    2. Completar:
    Campo Valor
    Name Intentos fallidos de login
    Severity High
    Expression count(/mauro/log[/var/log/auth.log,"Failed password",,,skip],5m)>5

    1. Guardar el trigger.

    Funcionamiento: la alerta se activa cuando se detectan más de cinco eventos coincidentes en cinco minutos.

    Esta detección puede ayudar a identificar intentos repetidos de acceso no autorizado. No confirma por sí sola un ataque de fuerza bruta.

    Si el item no puede leer el archivo, comprobar los permisos y la configuración del agente. No otorgar permisos generales de lectura a todos los usuarios solo para hacer funcionar el monitoreo.

    Forzar Alerta por SSH o terminal de Ubuntu¶

    Ejecutar el siguiente bucle en la terminal de Ubuntu:

    for i in {1..3}; do
    ssh adrian@100.84.117.85 -o PreferredAuthentications=password -o PubkeyAuthentication=no
done

    Descripción:

    • for i in {1..3}: repite el intento de conexión seis veces.
    • ssh usuario_invalido@localhost: intenta conectarse mediante SSH utilizando un usuario inexistente.
    • PreferredAuthentications=password: prioriza la autenticación mediante contraseña.
    • PubkeyAuthentication=no: deshabilita la autenticación mediante claves públicas.

    Cuando solicite la contraseña, introducir una contraseña incorrecta o completar el intento fallido. Repetir hasta finalizar los seis intentos.

    Ejecutar el siguiente bucle en la terminal PowerShell de windows

    for ($i=1; $i -le 3; $i++) { ssh adrian@100.84.117.85 -o PreferredAuthentications=password -o PubkeyAuthentication=no }

    Verificar los registros del sistema¶

    Una vez realizados los intentos, comprobar que los errores se hayan registrado en el archivo de autenticación:

    sudo tail -n 10 /var/log/auth.log | grep "Failed password"

    Resultado esperado: deberían aparecer líneas similares a las siguientes:

    Failed password for invalid user usuario_invalido from 127.0.0.1 port 45678 ssh2

    Cada línea representa un intento de autenticación fallido registrado por el sistema.

    Comprobar la alerta en Zabbix¶

    Una vez que el agente activo envíe los registros al servidor, verificar la información desde:

    Monitoreo → Datos más recientes

    También se puede consultar:

    Monitoreo → Problemas

    La expresión del trigger utilizada es:

    count(/Notebook Ubuntu/log[/var/log/auth.log,"Failed password"],5m)>2

    Resultado esperado¶

    Intentos fallidos en 5 minutos Estado
    0 a 2 intentos OK
    Más de 2 intentos PROBLEM

    Aqui ya se resuelve por si solo el problema a travez de una expresion que dice si no hay mas de 2 intentos fallidos en los ultimos 5 minutos el problema se resuelve automaticamente

    count(/adrian/log[/var/log/auth.log,"Failed password"],5m)<2

    Importante: el resultado depende de que el servicio SSH esté activo, el agente Zabbix tenga permisos para leer /var/log/auth.log y el ítem log[] esté configurado como chequeo activo. Los intentos deben quedar registrados dentro de la ventana de cinco minutos.

    Importante: para monitorizar logs de forma continua, el agente debe admitir comprobaciones activas y tener configurado correctamente el servidor Zabbix. El usuario del agente también debe disponer de permisos de lectura sobre el archivo.

    8. Tráfico de red entrante¶

    Equipo: NOTEBOOK UBUNTU
    Objetivo: detectar un volumen elevado de tráfico entrante en una interfaz de red.

    8.1. Identificar la interfaz de red¶

    Antes de crear el item, ejecutar en Ubuntu:

    ip -br addr

    Identificar la interfaz que se desea monitorear, por ejemplo ens33, enp0s3 o eth0.

    El nombre depende de la configuración de cada equipo.

    8.2. Crear el item¶

    1. Seleccionar NOTEBOOK UBUNTU en Zabbix.
    2. Abrir Items → Create item.
    3. Configurar:
    Campo Valor
    Name Tráfico de red entrante
    Type Zabbix agent
    Key net.if.in[ens33]
    Type of information Numeric (int 64 bits)
    Host name 127.0.0.1:10050
    Units Bps
    Update interval 10s
    Enabled Sí
    1. En Preprocessing, agregar el paso Change per second para convertir el contador acumulado de bytes en una tasa de transferencia.

    1. Guardar el item.

    Importante: reemplazar ens33 por el nombre real de la interfaz. La unidad Bps representa bytes por segundo; no equivale a bits por segundo.

    8.3. Crear el trigger¶

    1. Abrir Triggers → Create trigger.
    2. Completar:
    Campo Valor
    Name Consumo de tráfico entrante elevado (>100 Mbps
    Severity Warning
    Expression last(/adrian/net.if.in[wlx70f1a17d3701,bytes]) - last(/adrian/net.if.in[wlx70f1a17d3701,bytes],#7)>125000

    1. Guardar el trigger.

    Funcionamiento: se genera una alerta cuando el promedio de tráfico entrante supera los 10 MiB/s durante cinco minutos.

    El umbral es un ejemplo inicial y debe ajustarse al uso habitual de la red.

    Forzar alerta trafico entrante¶

    Para realizar pruebas de tráfico de red entre Windows y Ubuntu, utilizaremos iperf3. Esta herramienta permite generar tráfico controlado y medir el rendimiento de la conexión.

    Descargar iperf3¶

    Ingresar a la siguiente página:

    Descargar iperf3 para Windows

    Buscar la sección Windows y descargar una versión compatible de 64 bits.

    Extraer los archivos¶

    1. Abrir el archivo ZIP descargado.
    2. Extraer su contenido en una carpeta llamada C:\iperf3.
    3. Comprobar que estén presentes los archivos iperf3.exe y, si viene incluido, cygwin1.dll.

    Ejecutar desde PowerShell¶

    Abrir PowerShell y acceder a la carpeta:

    cd C:\iperf3
.\iperf3.exe --version

    Si aparece la información de la versión, la herramienta está lista para utilizarse.

    Realizar la prueba de tráfico¶

    En Ubuntu, ejecutar el servidor de iperf3:

    iperf3 -s

    En Windows, ejecutar el cliente:

    .\iperf3.exe -c IP_DE_UBUNTU -R -t 120

    Descripción de los parámetros:

    • -c: indica que se ejecutará como cliente.
    • IP_DE_UBUNTU: dirección IP del equipo Ubuntu.
    • -R: invierte el sentido del tráfico para que Ubuntu envíe datos y Windows los reciba.
    • -t 120: establece una duración de 120 segundos (2 minutos).

    Genero trafico entre windows y ubuntu para forzar la alerta

    Resultado esperado¶

    La prueba generará tráfico de red durante dos minutos. Esto permitirá comprobar la comunicación entre ambos equipos y generar actividad para verificar las métricas de tráfico entrante en Windows mediante Zabbix.

    Importante: ESnet no ofrece soporte oficial para iperf3 en Windows. Las versiones disponibles para este sistema operativo son compilaciones de terceros.

    9. Verificación de los items y triggers¶

    Una vez creados los ocho items y sus respectivos triggers, realizar las siguientes comprobaciones.

    9.1. Verificar los items¶

    1. Ir a Data collection → Hosts.
    2. Seleccionar el equipo correspondiente.
    3. Abrir Items.
    4. Confirmar que los items estén habilitados y que reciban valores recientes.
    5. Revisar la columna de estado y los errores de recopilación.

    9.2. Verificar los triggers¶

    1. Abrir Monitoring → Problems.
    2. Comprobar que las alertas aparezcan cuando se cumplan sus condiciones.
    3. Verificar la severidad asignada.
    4. Confirmar que el problema se recupere cuando la condición deje de cumplirse.

    9.3. Consideraciones finales¶

    • Los nombres técnicos de los hosts usados en las expresiones deben coincidir exactamente con los registrados en Zabbix.
    • Los items y triggers deben estar habilitados.
    • Los agentes deben tener conectividad con el servidor y una configuración compatible con el tipo de comprobación.
    • Los umbrales propuestos son valores iniciales y pueden necesitar ajustes según el comportamiento normal de cada equipo.
    • No generar una alerta real de fuerza bruta ni interrumpir servicios críticos en producción solo para probar las configuraciones. Utilizar un entorno controlado.
