    Monitoreo de red mediante SNMP en Zabbix¶

    1. Introducción¶

    SNMP (Simple Network Management Protocol) permite consultar información de dispositivos y sistemas de red, como interfaces, tráfico, estado y estadísticas de funcionamiento.

    En esta práctica configuraremos un equipo para que Zabbix pueda consultar sus métricas mediante SNMP a través de Tailscale. También utilizaremos ICMP para medir la latencia y generar una alerta cuando el tiempo de respuesta supere un umbral definido.

    Objetivos¶

    • Instalar y configurar el servicio SNMP.
    • Permitir las consultas desde el servidor Zabbix a través de Tailscale.
    • Registrar el equipo en Zabbix mediante una interfaz SNMP.
    • Asociar plantillas de monitoreo.
    • Generar una condición de advertencia mediante un umbral de latencia.

    2. Configuración del equipo Linux¶

    2.1. Habilitar el enrutamiento IP¶

    El siguiente comando habilita temporalmente el reenvío de paquetes IPv4 en el núcleo de Linux:

    sudo sysctl -w net.ipv4.ip_forward=1

    Importante: este parámetro solo es necesario si el equipo debe reenviar tráfico entre interfaces, por ejemplo, si actúa como router. No es un requisito para instalar SNMP ni para que Zabbix consulte un agente SNMP a través de Tailscale.

    Para comprobar su valor:

    sysctl net.ipv4.ip_forward

    Si el resultado es net.ipv4.ip_forward = 1, el reenvío está habilitado.

    2.2. Instalar el servicio SNMP¶

    Actualizar los repositorios e instalar el servicio:

    sudo apt update
sudo apt install snmpd snmp -y
    • snmpd: servicio que responde a las consultas SNMP.
    • snmp: herramientas cliente para realizar pruebas desde la terminal.

    Comprobar el estado del servicio:

    sudo systemctl status snmpd

    Habilitar el inicio automático y arrancar el servicio:

    sudo systemctl enable --now snmpd

    2.3. Configurar el servicio SNMP¶

    Abrir el archivo de configuración:

    sudo nano /etc/snmp/snmpd.conf

    Buscar la directiva agentaddress. En una configuración predeterminada puede aparecer de esta forma:

    agentaddress 127.0.0.1,[::1]

    Esta configuración limita la escucha a las interfaces locales. Para permitir consultas remotas, hay que modificarla para que SNMP escuche en la interfaz adecuada.

    Configuración recomendada: utilizar la IP de Tailscale del equipo supervisado, si está disponible y corresponde a la interfaz por la que se realizarán las consultas.

    Ejemplo ilustrativo:

    agentaddress udp:100.112.1.18:161

    Reemplazar 100.112.1.18 por la IP de Tailscale real del equipo donde está instalado snmpd. Si esa dirección corresponde al router u otro equipo, no debe utilizarse aquí.

    Si se necesita escuchar en todas las interfaces, puede utilizarse:

    agentaddress udp:161

    Sin embargo, esta alternativa requiere restringir el acceso mediante el firewall y la configuración de SNMP.

    2.4. Configurar la comunidad de lectura¶

    En el archivo snmpd.conf, localizar la directiva de comunidad de solo lectura.

    Una configuración como esta:

    rocommunity public default -V systemonly

    limita las consultas a una vista de información del sistema. No debe eliminarse esa restricción sin evaluar las consecuencias.

    Para un laboratorio, si se decide utilizar SNMPv2c, se debe definir una comunidad propia y limitar el origen autorizado. Por ejemplo, la siguiente línea ilustra una restricción al servidor Zabbix:

    rocommunity NOMBRE_COMUNIDAD 100.69.187.108

    En este ejemplo, 100.69.187.108 representa la IP de Tailscale del servidor Zabbix y NOMBRE_COMUNIDAD debe reemplazarse por una comunidad propia. No utilizar literalmente ese nombre.

    Seguridad: SNMPv2c transmite la comunidad sin cifrado. La consulta debe limitarse a una red confiable, como Tailscale, y a los orígenes autorizados. Para entornos más exigentes, considerar SNMPv3 con autenticación y privacidad.

    Guardar el archivo con Ctrl + O, confirmar con Enter y salir con Ctrl + X.

    2.5. Reiniciar y verificar SNMP¶

    Aplicar los cambios:

    sudo systemctl restart snmpd

    Verificar el estado:

    sudo systemctl status snmpd

    Comprobar que el servicio esté escuchando en el puerto UDP 161:

    sudo ss -lunp | grep ':161'

    Si el servicio no inicia, revisar los registros:

    sudo journalctl -u snmpd -n 50 --no-pager

    2.6. Comprobar el firewall¶

    Si se utiliza UFW, verificar las reglas actuales:

    sudo ufw status verbose

    Si las consultas se realizan exclusivamente desde la IP de Tailscale del servidor Zabbix, se puede restringir el acceso a ese origen:

    sudo ufw allow in on tailscale0 from 100.69.187.108 to any port 161 proto udp

    La interfaz tailscale0 y la dirección de origen deben coincidir con la configuración real del entorno.

    3. Crear el equipo en Zabbix¶

    3.1. Abrir el formulario de creación¶

    1. Ingresar a la interfaz web de Zabbix.
    2. Ir a Recopilación de datos → Equipos (Data collection → Hosts), o a la sección equivalente según la versión.
    3. Pulsar Crear equipo.

    3.2. Configurar los datos básicos¶

    Completar los campos de la siguiente manera:

    Campo Valor
    Nombre del equipo RTR-CORE
    Grupos de equipos Routers o un grupo apropiado
    Tipo de interfaz SNMP
    Dirección IP 100.112.1.18, si es la IP de Tailscale del dispositivo supervisado
    Puerto 161
    Versión SNMP SNMPv2
    Comunidad SNMP {$SNMP_COMMUNITY} o el valor configurado en el agente

    Si se utiliza la macro {$SNMP_COMMUNITY}, hay que definirla en el equipo, en una plantilla o en un nivel superior con el mismo valor configurado en snmpd.conf.

    Aclaración: si RTR-CORE es un router físico, no se instala snmpd en él como si fuera Ubuntu. En ese caso, debe habilitarse SNMP en el propio router. La configuración de Ubuntu descrita en la sección anterior corresponde a un equipo Linux que ejecuta el servicio SNMP.

    3.3. Asociar las plantillas¶

    En la pestaña Plantillas (Templates), asociar las plantillas apropiadas para el dispositivo y los objetivos de monitoreo.

    • ICMP Ping: permite comprobar la respuesta del dispositivo mediante ICMP y obtener métricas relacionadas con su disponibilidad y latencia.
    • Linux by SNMP: permite recopilar métricas del sistema Linux mediante SNMP, siempre que el agente exponga los datos necesarios y la plantilla sea compatible.

    Los nombres exactos pueden variar según la versión de Zabbix y las plantillas instaladas. Si el equipo es un router físico, utilizar una plantilla compatible con su fabricante o sistema operativo en lugar de una plantilla específica de Linux.

    3.4. Guardar y verificar¶

    1. Pulsar Añadir para guardar el equipo.
    2. Regresar al listado de equipos.
    3. Esperar a que se ejecuten las primeras comprobaciones.
    4. Actualizar la vista y revisar la disponibilidad SNMP.

    Si la configuración es correcta y las consultas tienen éxito, la disponibilidad SNMP debería aparecer en verde.

    3.5. Crear el disparador SNMP¶

    Para detectar problemas en la comunicación SNMP, se puede utilizar un disparador que genere un problema cuando Zabbix deje de recibir respuestas del dispositivo.

    1. Ir a Recopilación de datos → Equipos y seleccionar RTR-CORE.
    2. Acceder a la sección Disparadores (Triggers) y pulsar Crear disparador.

    3. Completar los campos:

    4. Nombre: Linux: High ICMP ping response time

    5. Severidad: Advertencia
    6. Expresión: utilizar una métrica SNMP que exista en el equipo y comprobar que no reciba datos durante el intervalo definido.

    Si se utiliza una plantilla compatible, es preferible aprovechar sus disparadores predefinidos para detectar la indisponibilidad SNMP, evitando duplicar alertas.

    1. Guardar el disparador y verificar que aparezca en la lista.

    2. Comprobar que la acción de notificación esté configurada para enviar alertas por Telegram o correo electrónico.

    Resultado esperado: si el dispositivo deja de responder a las consultas SNMP durante el período establecido, Zabbix debe generar un problema y enviar la notificación correspondiente, siempre que la expresión y la acción estén correctamente configuradas.

    La disponibilidad ICMP se verifica de forma independiente de la disponibilidad SNMP.

    Tambien la alerta se configuro para que llegue por Telegram

    4. Generar una alerta por latencia¶

    Para probar la detección de latencia, modificaremos temporalmente el umbral de advertencia del equipo de laboratorio.

    4.1. Localizar la macro¶

    1. Ir al listado de equipos y abrir RTR-CORE.
    2. Acceder a la pestaña Macros.
    3. Consultar las macros heredadas y las definidas para el equipo.
    4. Buscar:
    {$ICMP_RESPONSE_TIME_WARN}

    En algunas plantillas, el valor de advertencia puede ser 0.15, equivalente a 150 milisegundos.

    4.2. Modificar temporalmente el umbral¶

    Cambiar el valor por uno muy bajo, por ejemplo:

    0.001

    Esto equivale a un milisegundo si la plantilla interpreta el umbral en segundos.

    Guardar los cambios mediante Actualizar.

    4.3. Esperar y verificar el evento¶

    Esperar a que se ejecuten las comprobaciones ICMP y revisar los problemas en Zabbix.

    Si el tiempo de respuesta medido supera el umbral y el trigger asociado evalúa esa condición, debería generarse una advertencia.

    Importante: un umbral artificialmente bajo no garantiza que se genere el evento. Depende de las métricas disponibles, la expresión del trigger, sus condiciones y los intervalos de comprobación.

    4.4. Restaurar el valor original¶

    Una vez finalizada la prueba, volver a la macro y restaurar el valor anterior, por ejemplo:

    0.15

    No dejar el umbral de prueba en producción, ya que podría generar alertas innecesarias.
